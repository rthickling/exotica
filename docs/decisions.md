# Technical decisions and source boundaries

Checked 14 November 2026. Status words distinguish documented capability, inspected code, executed checks, synthetic assumptions and deferred integration. Execution evidence and exact commands are indexed in the README and valuation note; source links alone do not prove a run.

## Framework and persistence

**Selected (15 November 2026):** Docker Compose and `just` 1.56+ are the only installed development requirements. Shared justfiles import Unix and Windows adapters; native Windows uses its built-in PowerShell, without Git Bash or PowerShell 7. The Temurin JDK, Python/QuantLib tools and PostgreSQL run in containers. Default Java tests always use the isolated test Compose database; the application and test databases use separate networks and volumes. Tool containers map the invoking user on Unix and use Docker Desktop bind-mount ownership on native Windows. Build reports and evidence remain in the checkout.

**Documented; selected:** Java21, Spring Boot3.5.16 and checksum-pinned Gradle8.14.3 with Kotlin DSL. `app/build.gradle.kts` imports the Spring Boot3.5.16 BOM using Gradle native platform support. The [Boot Gradle guide](https://docs.spring.io/spring-boot/3.5/gradle-plugin/getting-started.html) documents plugin and BOM support. Java21 compatibility is documented in the [3.5 system requirements](https://docs.spring.io/spring-boot/3.5/system-requirements.html). Use `just build-app` or the app justfile; recipes run `app/gradlew` in the Temurin JDK container, so no host Java or Gradle installation is needed.

**Documented; verify through the actual call path:** Spring's [6.2 transaction annotation reference](https://docs.spring.io/spring-framework/reference/6.2/data-access/transaction/declarative/annotations.html) explains default proxy interception, the self-invocation limitation and default rollback for runtime exceptions/errors rather than checked exceptions. Booking must enter the service through a Spring-managed external call. The deliberately injected rollback check and persisted table inspection establish this application's behaviour; an annotation in source does not establish it.

**Inspected in source:** `Persistence.java` uses `Enquiry.version` with `@Version`. `V1__core.sql` separately constrains one trade per enquiry, unique idempotency keys and unique obligation event keys per trade. These protect different invariants. A version check alone is not durable idempotency; a Java in-memory guard alone cannot arbitrate multiple application instances. Concurrent requests and inspection of committed PostgreSQL rows are required evidence.

**Documented:** The [Hibernate6.6 fetching chapter](https://docs.hibernate.org/orm/6.6/userguide/html_single/Hibernate_User_Guide.html#fetching) distinguishes when an association loads from how it loads. Separate association selects can produce N+1 queries; laziness does not itself solve that problem. A fetch join or DTO query should match a particular use case. Accessing uninitialized associations after their session is closed can fail. The enquiry/offer mapping provides a concrete learning example; query evidence is required before claiming an optimisation.

## External boundaries

**Documented; deferred:** The [Deritrade connectivity reference](https://api-docs.deritrade.com/docs/Introduction/connectivity/) distinguishes Acceptance from Production and requires OAuth client credentials supplied by Vontobel. No authorised credentials or successful live call are claimed here. The default issuer gateway uses local fixtures. An adapter boundary permits later authorised integration.

**Simulated:** Staff/client eligibility records, issuer replies, matching outcomes, instruction authority, firm acceptance and payment/custody actions are controlled development examples. Issuer identity and credit labels are separate fixture information, not credit analysis. A higher coupon or lower strike is meaningful only within the declared comparison basis and does not establish a better investment.

**Business roles:** The selected note issuer owes the note's contractual payments. For the accumulator, the selected bilateral counterparty delivers shares against the investor's purchase cash; the simulator's shared `issuer` label does not make it a funded note issuer. The staff/distribution workflow gathers offers and records selection and authority; distribution alone does not make it the issuer. An issuer's possible hedge is a separate transaction with its own counterparty, and no hedge is booked here. Selecting an external issuer's note and issuing a separate note while hedging externally therefore remain different arrangements.

**Deferred:** Live market calibration, smile/skew, stochastic rates, issuer credit/funding, collateral and commercial costs; production identity, legal documentation, issuance/confirmation services, hedge books and settlement rails. Kafka/Avro transport is also deferred unless a separate executed publish/consume trace is delivered. A committed `TradeBooked` outbox record proves database commit only. Client and secondary-market interfaces are outside the selected system.
